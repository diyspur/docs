## 1. Otimização de RLS: O Padrão "InitPlan"

### 1.1 O Problema da Reavaliação Volátil por Linha
Por padrão, ao definir uma política RLS no PostgreSQL no formato:
```sql
-- Padrão ingenuo (lento em tabelas grandes):
CREATE POLICY "own_records" ON public.comments
  FOR SELECT USING (user_id = auth.uid());
```
O planejador de consultas do PostgreSQL avalia `auth.uid()` **para cada linha escaneada** ($O(N)$ avaliações). Em tabelas com milhares de comentários, diários ou históricos de progresso, isso degrada a latência e impede o uso otimizado de índices B-tree.

### 1.2 A Solução Arquitetural: Subquery Escalar `(SELECT auth.uid())`
O DIYSpur executa uma migração dedicada (`optimize_rls_auth_initplans.sql`) que normaliza automaticamente todas as políticas para:
```sql
-- Padrão otimizado DIYSpur (InitPlan):
CREATE POLICY "own_records" ON public.comments
  FOR SELECT USING (user_id = (SELECT auth.uid()));
```

```
┌────────────────────────────────────────────────────────────────────────┐
│                        COMO O POSTGRES OTIMIZA                         │
├────────────────────────────────────────────────────────────────────────┤
│  SEM SUBQUERY:                                                         │
│  Seq Scan on comments -> auth.uid() chamado 50.000 vezes               │
│  Latência: ~140ms                                                      │
├────────────────────────────────────────────────────────────────────────┤
│  COM (SELECT auth.uid()):                                              │
│  InitPlan 1 (returns $0) -> auth.uid() chamado 1 ÚNICA VEZ             │
│  Index Scan using comments_user_id_idx on comments (user_id = $0)      │
│  Latência: < 2ms (Ganho de 70x na p99)                                 │
└────────────────────────────────────────────────────────────────────────┘
```

## 2. Gateway e Autorização das Edge Functions (Deno)

O ecossistema DIYSpur opera 11 Edge Functions com governança centralizada em `supabase/functions/_shared/auth.ts`:

```mermaid
flowchart TD
    REQ["Requisição Externa / Webhook / Client"] --> GW["Supabase Edge Gateway"]
    
    GW -->|verify_jwt = true (Padrão)| CHECK_JWT{"Token JWT<br/>Válido?"}
    CHECK_JWT -->|Não| ERR_401["HTTP 401 Unauthorized"]
    CHECK_JWT -->|Sim| RUNTIME["Execução no Runtime Deno"]
    
    GW -->|verify_jwt = false (Exceções Únicas)| SPECIAL{"Tipo de Rota Especial"}
    SPECIAL -->|Stripe Webhook| STRIPE_AUTH["Verificação Criptográfica HMAC<br/>Header 'stripe-signature'"]
    SPECIAL -->|Scheduled Reminders| TIMING_AUTH["Token Secreto de Serviço<br/>Comparação em Tempo Constante"]
    
    RUNTIME --> DB_SERVICE["Acesso Transacional ao PostgreSQL<br/>(schema private + search_path='')"]
```

### 2.1 Matriz de Governança das Funções

| Função | Gateway `verify_jwt` | Mecanismo de Defesa Interno |
|---|---|---|
| `quiz-validate` | `true` | Extrai `auth.getUser()`, valida se o usuário possui sessão ativa e confere gabarito no schema `private`. |
| `award-xp` | `true` | Restrito; chamado internamente ou por client autenticado com verificação de idempotência anti-duplicação. |
| `next-book-vote` | `true` | Valida se a enquete ainda está aberta no horário do servidor e se o leitor já não computou voto anterior. |
| `stripe-webhook` | `false` *(Obrigatório)* | O gateway não possui JWT do Stripe. O handler reconstrói o payload bruto e valida a assinatura criptográfica usando `STRIPE_WEBHOOK_SECRET`. |
| `scheduled-reminders` | `false` *(Obrigatório)* | Invocado por cron jobs. Valida header de serviço usando algoritmo de comparação em tempo constante para eliminar *timing attacks*. |

## 3. Concorrência e Bloqueios Transacionais

Para prevenir condições de corrida em operações simultâneas de alta densidade, o DIYSpur implementa procedimentos específicos em PL/pgSQL:

### 3.1 Reordenação de Listas de Leitura (`reorder_reading_list`)
Ao reordenar uma lista de 50 livros arrastando e soltando (*drag-and-drop*), duas requisições simultâneas poderiam corromper a numeração sequencial. A RPC do banco bloqueia a linha da lista pai com `SELECT ... FOR UPDATE`:

```sql
-- Bloqueia a lista pai para gravação concorrente
SELECT version FROM public.reading_lists 
WHERE id = p_list_id FOR UPDATE;

-- Incrementa a versão otimista
UPDATE public.reading_lists 
SET version = version + 1 
WHERE id = p_list_id;
```

### 3.2 Criação Atômica de Clubes com Idempotência
Para impedir que cliques repetidos criem múltiplos clubes com o mesmo nome, o backend exige um UUID de requisição (`client_request_id`) gerado no frontend, utilizado como chave de idempotência na transação de inserção.

## 4. O Problema da Prova Física de Leitura

Uma distinção arquitetural vital no design do DIYSpur:
- **Progresso Autodeclarado (`user_progress.percent`):**  
  Existe para conveniência e conforto do leitor na interface. O leitor pode marcar que leu 80% ou 100% para destravar visualmente comentários e organizar sua estante.
- **Validação Efetiva (Prova de Hábito):**  
  O sistema **não concede XP nem medalhas baseado puramente no percentual autodeclarado**. A concessão de XP e a progressão em desafios exigem a realização bem-sucedida do **Quiz Pedagógico**, cujas respostas são validadas contra o gabarito protegido pelo servidor.

## 5. Isolamento da Superfície de Ataque: Desacoplamento do Console Admin

Como medida avançada de segurança da informação e performance de entrega de assets:
- **Separação Física de Repositórios:** O código operacional e editorial (`/admin/**`) foi completamente extraído do repositório `app` e isolado no projeto dedicado [`diyspur/admin`](https://github.com/diyspur/admin).
- **Eliminação de Vazamento de Rotas no Bundle Público:** O bundle de produção entregue aos leitores não contém mais referências, metadados ou Server Actions ligadas à administração de temporadas, catálogo e moderação de denúncias.
- **Defesa em Profundidade:**
  1. **Nível de Banco (RLS & RPCs):** A função `public.is_admin()` e o schema `private` continuam sendo a barreira definitiva de execução no PostgreSQL.
  2. **Nível de Aplicação:** O console admin possui middleware próprio com auto-login e gestão de credenciais dedicadas.
  3. **Nível de Rede e Varredura:** O aplicativo público do leitor responde imediatamente com 404 (Not Found) a qualquer tentativa de escaneamento de rotas administrativas.
